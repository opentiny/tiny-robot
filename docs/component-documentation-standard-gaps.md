# 组件文档规范验证缺陷

本文记录使用《组件文档规范》重整 Bubble 与 Sender 文档时发现的规则冲突、歧义、缺失和执行成本问题，作为后续修订规范的输入。

本次验证遵循两项边界：组件源码和公开行为是事实来源；本文只记录规范问题，不在本分支修改规范正文。

## 冲突

### G1. 标准结构与参考分支页面不一致

- **规则或空白**：规范 4.1 建议组件页统一使用 `outline: [1, 3]`，并采用“概览、快速开始、用法示例、API、迁移与弃用”的大章节结构。
- **实际案例**：规范分支中的 Bubble 仍使用 `outline: [1, 4]`，Bubble 与 Sender 也分别使用“代码示例”“输入增强”“交互定制”等旧结构。
- **影响**：作者无法判断规范分支中的页面是待迁移案例，还是可以直接复制的参考实现。
- **本次裁决**：以规范正文为目标，两篇页面都采用 `outline: [1, 3]` 和标准大章节。
- **建议规则**：规范发布时同时指定一篇已经完全迁移的复杂组件作为基准页面，并在未迁移页面顶部明确标记状态。

### G2. Events 与 Emits 的术语不一致

- **规则或空白**：标准 API 模板使用 `Events`，没有说明何时可以使用 Vue 的 `Emits` 术语。
- **实际案例**：参考分支的 Bubble 使用 `Emits`，Sender 使用 `Events`。
- **影响**：同一站点的目录和跨页检索词不一致，作者也容易把实现术语与面向读者的 API 名称混用。
- **本次裁决**：两篇页面统一使用 `Events`；正文仍可用“触发事件”描述 Vue emit 行为。
- **建议规则**：明确规定面向读者的章节名固定为 `Events`，只有解释 Vue 类型或实现签名时使用 `emits`。

## 歧义

### G3. 复杂组件的标准学习层级缺少映射方法

- **规则或空白**：规范给出 L0～L5 的推荐顺序，但没有说明一个复杂组件的任务域如何映射到这些层级，也没有要求把层级名称直接作为标题。
- **实际案例**：Bubble 同时包含内容展示、消息列表和渲染器体系；Sender 同时包含输入状态、编辑器扩展、操作按钮、语音服务和外部内容。
- **影响**：机械套用“常用变体、状态与反馈、组合与定制”会把不同任务混在一起；完全采用组件特有标题又可能被误判为不符合规范。
- **本次裁决**：保留标准的大章节，在“用法示例”下使用面向任务的组件特有标题，并按由浅入深的顺序排列。
- **建议规则**：明确 L0～L5 是内容深度和排序约束，不是固定标题；补充“先按任务域分组，再在组内渐进”的复杂组件示例。

### G4. 主学习路径与高级外部集成的边界不清

- **规则或空白**：规范要求示例确定、可恢复且不依赖不可控服务，同时又允许 L5 高级与边界场景，没有说明真实服务集成文档怎样合规。
- **实际案例**：Sender 的语音材料包含浏览器权限、录音 API、服务端代理、鉴权和 WebSocket；这些信息有参考价值，但无法成为开箱即用的稳定 Demo。
- **影响**：严格删除会损失高级接入信息，直接保留又会让读者把占位配置误认为可运行方案。
- **本次裁决**：主示例使用本地 Mock handler；真实服务代码作为高级参考，明确列出权限、代理和凭据保护责任。
- **建议规则**：增加“可运行 Demo”和“集成参考代码”两种产物类型，并分别规定运行性、凭据、安全提示和展示方式。

### G5. 迁移提醒的页面位置没有去重规则

- **规则或空白**：模板把“迁移与弃用”放在页面末尾，但没有说明重大升级提示能否同时出现在首屏。
- **实际案例**：Bubble 与 Sender 都需要让旧用户尽早看到 v0.4 提示；Sender 还包含较长的移除 API 映射。
- **影响**：全部放在末尾可能让升级用户错过风险，全部放在顶部又会打断新用户的快速开始。
- **本次裁决**：顶部保留简短警告与迁移入口，详细兼容说明和移除项集中到文末。
- **建议规则**：规定“首屏摘要 + 文末详情”的双层模式，并要求首屏只包含版本、影响范围和详情链接。

## 缺失

### G6. 缺少 Demo 保留、合并和删除的判定标准

- **规则或空白**：规范要求每个 Demo 有一个主要学习目标，但没有说明多个相近 Demo 应保留、合并还是拆分。
- **实际案例**：Bubble 的 `provider-renderer.vue` 在同一页面重复引用；Sender 的 Suggestion 基础、过滤和高亮示例既有连续学习关系，也有较多重复设置代码。
- **影响**：不同作者可能为了覆盖率保留重复示例，或为了页面长度合并成难以理解的综合示例。
- **本次裁决**：删除 Bubble 的重复引用；Sender 暂时保留三个 Suggestion 示例，因为它们分别回答默认行为、过滤策略和展示策略。
- **建议规则**：增加决策表：学习目标相同则合并或删除；前置知识与观察结果不同则拆分；只有代码设置重复不能单独作为合并理由。

### G7. “结果可观察”缺少读者侧判定

- **规则或空白**：规范要求主要操作形成可观察结果，但没有明确控制台日志、浏览器弹窗或只改变内部状态是否合格。
- **实际案例**：Sender 多个示例把提交结果或选择结果只写入 `console.log`，默认按钮示例使用 `alert`；Bubble 图片示例的结果受远程随机服务控制。
- **影响**：读者需要打开开发者工具，自动截图无法验证结果，弹窗还会中断连续阅读。
- **本次裁决**：核心事件结果使用示例内的状态区展示，并在适用时使用 `aria-live`；控制台只用于调试教学，弹窗不作为主要结果。
- **建议规则**：将“无需开发者工具即可观察、可重复触发、可恢复”加入 Demo 检查清单，并说明异步结果、错误和取消状态的最低展示要求。

### G8. 复合组件 API 的聚合方式未定义

- **规则或空白**：标准只展示单组件的 Props、Events、Slots、Methods、Types 和 CSS Variables，没有规定主组件携带子组件或 Provider 时如何组织。
- **实际案例**：Bubble 页面同时记录 `Bubble`、`BubbleList`、`BubbleProvider`；Sender 页面同时记录 `Sender`、`UploadButton`、`VoiceButton` 和编辑器扩展。
- **影响**：所有 API 放在一页会产生很长的章节，拆页又可能破坏任务流和搜索入口；方法也容易被错误地夹在 Props 中。
- **本次裁决**：保留同页聚合，在标准 API 大类下用四级标题区分所属组件或扩展。
- **建议规则**：补充复合组件矩阵，按“是否独立导出、是否独立使用、API 规模、是否共享任务流”决定同页分组或独立页面。

### G9. Demo 元数据没有自动校验规则

- **规则或空白**：规范要求标准和复杂组件的 Demo 提供有效 `title` 与 `description`，但没有定义有效性，也没有配套检查命令。
- **实际案例**：参考分支的 Sender Demo 已包含元数据，而 Bubble 的全部 Demo 引用均缺失；两种状态都能通过 VitePress 构建。
- **影响**：要求容易在批量迁移中遗漏，代码评审只能人工逐项检查。
- **本次裁决**：本次为 Bubble 所有引用补齐能说明任务和观察结果的标题、描述。
- **建议规则**：提供 lint 规则或脚本，至少检查复杂组件的 `<demo>` 是否同时包含非空 `title`、`description`，并给出避免复述标题的示例。

## 执行成本

### G10. 复杂页面的 API 审计缺少工具和增量边界

- **规则或空白**：标准要求 Props 使用 kebab-case、说明行为和联动、标注默认值与必填性；Types 还要求索引表和导出入口。
- **实际案例**：Bubble 与 Sender 的既有 API 表规模大、混合多个子组件，并使用 camelCase、`-` 与 `undefined` 等旧格式。
- **影响**：规范的 MUST 要求意味着实质性重整复杂页面时必须同步完成字段级审计，但规范没有说明“当前改动范围”的边界，也没有生成公开导出索引或检测命名、默认值的工具，容易漏项或误报公共契约。
- **本次裁决**：不把执行成本视为豁免；本次按包根导出、公开类型和实现完成 Props、Events、Slots、Methods / Expose 与 Types 的审计，并把仍需维护者确认的 CSS Variables 单独保留为 G11。
- **建议规则**：明确“实质性修改”触发完整 API 审计的判定条件，并提供从 TypeScript 公共导出生成初始索引、检查 kebab-case 和必填列的工具。

### G11. CSS Variables 的公共资格难以由文档作者独立验证

- **规则或空白**：规范要求只有可追溯到公共契约或维护者确认的变量才能进入文档，但没有指定确认记录或机器可读来源。
- **实际案例**：Bubble 与 Sender 已有大量 CSS Variables 表格，源码使用情况只能证明变量存在，不能证明长期兼容承诺。
- **影响**：作者只能沿用历史表格或逐项询问维护者，无法稳定完成“完整且不误报”的审计。
- **本次裁决**：保留已发布文档中的变量，不把本次源码扫描发现的新变量自动加入公共 API。
- **建议规则**：在主题 token、源码注释或清单文件中增加公共标记，并要求文档表格链接到该事实源。

## 实施中发现的 API 事实冲突（非规范缺陷）

以下问题来自当前公开类型与运行时实现之间的差异，不归因于文档规范，但会影响文档能否同时忠实于两类事实源。

### A1. Sender 插槽作用域类型与转发实现不一致

- `SenderSlots` 声明 `actions-inline`、`footer` 和 `footer-right` 接收 `SenderSlotScope`。
- `TrSender` 的顶层插槽转发没有传递这些 `slotProps`，当前运行时只有 `content` 插槽能收到 `editor`。
- 本次文档按当前可用行为记录为“无作用域参数”，不修改组件行为。后续需要决定是修复顶层转发，还是收窄公开类型。

### A2. BubbleList 的自定义分组函数没有公开类型名

- `BubbleListProps.groupStrategy` 使用内部 `BubbleGroupFunction`，但该类型没有从包根导出。
- 本次 Props 表使用完整函数签名，避免暗示开发者可以直接导入该类型。
- 后续可以公开 `BubbleGroupFunction`，或在公共类型中直接内联该签名并移除内部命名。

### A3. SenderSuggestionItem.label 的类型说明与运行时不一致

- 公开类型把 `label` 描述为显示文本，并称未提供时使用 `content`。
- 当前 Suggestion 列表的高亮、展示和默认回填都只读取 `content`，没有消费 `label`。
- 本次文档把 `label` 记录为当前未参与展示和回填的可选元数据。后续需要实现类型所承诺的显示行为，或收窄字段说明。
