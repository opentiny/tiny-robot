# `polish-opentiny-article` 独立化设计

日期：2026-06-22

## 1. 背景

`polish-opentiny-article` 用于优化 OpenTiny 对外技术文章。当前工作区中的草案把通用改写规则整体复制到 Skill 内部，又通过第二层入口调用，带来以下问题：

- Skill 的职责被拆成文章工作流和通用语气处理两层，理解和维护成本偏高。
- 大量聊天、社区帖、README、release note 等规则与 OpenTiny 技术文章无关。
- 运行时需要加载过多材料，增加上下文消耗和规则冲突。
- 上游规则允许的部分改写方式不符合 OpenTiny 的事实保护要求。
- 目录、测试和需求文档需要持续维护外部项目的名称、来源和版本信息。

本次调整将 Skill 改为面向 OpenTiny 文章优化的独立实现。

## 2. 已确认决策

1. 只保留一个顶层 Skill：`polish-opentiny-article`。
2. 不创建或嵌套 `tone`、`shuorenhua` 等子 Skill。
3. 不保留 `LICENSE.shuorenhua`、上游仓库、固定 Commit 或本地修改说明。
4. 不继续复制或轻改上游正文；所有运行规则和示例均围绕本项目需求独立编写。
5. `polish-opentiny-article` 直接负责文章优化，包括初稿全文优化和 Draft PR 局部修订。
6. 安装入口和调用名称保持不变，`generate-opentiny-article` 继续调用该 Skill。

## 3. 目标

- 降低 OpenTiny 技术文章中的模板感、空话、营销腔和表演性技术表达。
- 保留事实、术语、责任主体、条件、数字、代码和其他受保护内容。
- 根据初稿生成、全文润色和局部 Review 三种场景控制修改范围。
- 将运行时规则压缩为项目真正需要的内容，避免加载无关场景资料。
- 使 Skill 可以由 Codex 和 Claude Code 独立理解和执行。
- 通过确定性检查和代表性样本验证 Skill 的结构、边界与实际行为。

## 4. 非目标

- 不提供通用聊天、私聊安慰、社交媒体或任意品牌文案润色能力。
- 不模拟特定作者的个人 voice。
- 不承担选题发现、新增资料调研、事实创建或文章发布；只核验写作计划已经固定的来源。
- 不修改代码示例、图表源文件或文章素材。
- 不自动处理未授权用户或 bot 的 Review 指令。
- 不建立独立的通用语气引擎、规则 DSL 或自动短语扫描器。

## 5. Skill 结构

```text
skills/polish-opentiny-article/
├── SKILL.md
└── references/
    ├── article-guardrails.md
    ├── style-guide.md
    ├── anti-patterns.md
    └── examples.md
```

所有 reference 都是 `polish-opentiny-article` 的普通内部资料，不带 Skill frontmatter，也不能作为独立 Skill 触发。

### 5.1 `SKILL.md`

作为唯一入口，保持精简并包含：

- 触发条件和职责范围。
- 初稿全文优化、全文润色和局部修订的范围判断。
- 必读 reference 的选择规则。
- 完整执行顺序。
- 失败与停止条件。
- 文章校验和 Draft PR 更新命令。
- 完成门槛。

核心流程必须能只读 `SKILL.md` 就被理解；详细判断规则按需读取 reference。

### 5.2 `article-guardrails.md`

作为修改边界的唯一权威来源，定义：

- 规则冲突优先级。
- 可修改的正文区域。
- 必须逐字保留的内容。
- 事实、术语、来源和人工修改保护要求。
- 全文优化与局部修订的范围边界。
- 修改后的保真回读清单。

其他文件不得重复维护完整保护清单，只能引用该文件。

### 5.3 `style-guide.md`

定义改写后的正向目标：

- 先写清主体、动作、条件和结果。
- 技术判断落到来源已有的事实或示例。
- 保持专业、克制、可直接发布的正式度。
- 允许自然长短句和必要转场，不追求整齐划一。
- 保留技术社区常用英文原词，避免生硬翻译和括注式中英堆叠。
- 不为制造“人味”补充个人经历、情绪或未经来源支持的细节。

该文件只描述“应该写成什么样”，不重复反模式列表。

### 5.4 `anti-patterns.md`

只保留 OpenTiny 技术文章中常见的问题族：

- 空泛时代背景和宏大开场。
- 无信息量的总结与价值拔高。
- 营销词、商业黑话和能力夸大。
- 表演性技术腔和不必要的 debug 叙事。
- 为制造洞见而使用的二元对比骨架。
- 无来源的权威判断、性能结论和用户反馈。
- 机械列点、句式过度对称和段落节奏过匀。
- 正文在公告腔、自媒体腔、聊天腔和技术说明之间漂移。

每类规则按“识别信号、推荐动作、保留条件”描述。规则以问题模式为主，不维护追求穷举的禁用词库。

### 5.5 `examples.md`

只放 OpenTiny 技术文章相关的独立示例：

- 技术文章开头去除宏大铺垫。
- 产品能力介绍降低营销强度。
- 技术方案说明保留 API、参数和条件。
- 事故或性能段落保留数字、责任主体和结论强度。
- 长文保留必要转场和节奏。
- Review 局部修订不扩散到其他章节。
- 信息不足时保留原文并请求人工确认。

示例不得通过虚构数字、用户反馈或产品能力来“改善”原文。需要具体信息时，只能使用示例原文已经提供的材料。

## 6. 输入场景与修改范围

### 6.1 初稿全文优化

触发方式：`generate-opentiny-article` 在正文生成完成后调用。

允许：

- 处理全部正文自然语言。
- 删除不承载信息的整句空话。
- 合并语义重复的相邻句。
- 在同一章节内调整句序或段落落点。
- 调整非受保护的二级及以下标题。

禁止：

- 改变文章主题、大纲意图或章节职责。
- 新增来源没有提供的事实、数字、案例或承诺。
- 修改 Front Matter、一级标题和受保护内容。

### 6.2 `/ai 全文润色`

处理全部正文，但比初稿全文优化更保守：

- 可以删除纯空话和修正明显的结构重复。
- 不主动重排章节。
- 不覆盖人工提交后形成的事实、观点和表达边界。
- 遇到可能改变作者判断或文章节奏的整句删除时，保留原文并说明风险。

### 6.3 Review 局部修订

触发来源：

- `Request changes`。
- 授权用户发出的 `/ai` 指令。
- 人工直接说明的局部修改要求。

默认行为：

- 只修改评论指向的行、段落或受影响章节。
- 不顺手优化相邻章节。
- 不重排段落，不删除未被意见覆盖的人工内容。
- 修改意见与固定来源冲突时停止，并请求人工裁决。

## 7. 执行流程

1. 读取文章、写作计划、来源快照、修改意见和当前 Head SHA。
2. 确定本轮属于初稿全文优化、全文润色还是局部修订。
3. 读取 `article-guardrails.md`，标记受保护内容和允许修改的范围。
4. 读取 `style-guide.md` 和 `anti-patterns.md`；只有需要校准边界时才读取 `examples.md`。
5. 第一遍按范围优化正文：
   - 删除不承载信息的提示层和空话。
   - 将抽象包装改为原文已有的具体主体、动作、条件和结果。
   - 统一文章内部语域。
   - 保留必要转场、技术术语和文章节奏。
6. 执行保真回读：
   - 核对事实、数字、条件、时间线、责任主体和结论强度。
   - 核对 Front Matter、标题、代码、API、命令、路径、链接和图表源内容。
   - 核对是否只修改了本轮授权范围。
7. 执行自然度回读：
   - 检查是否仍有空开场、空总结、营销腔、无源引用或表演性技术腔。
   - 只做轻量修正，不开启第二轮全文重写。
8. 涉及事实、版本、API、兼容性或性能结论时回到固定来源核验；无法确认则保留原文并请求人工判断。
9. 运行文章校验。
10. 校验通过后更新 Draft PR；需要时回写 Issue 状态。

## 8. 冲突处理与停止条件

优先级从高到低：

1. 固定来源、已批准写作计划中的事实和受保护内容。
2. 不改变上述事实与保护边界的人工明确要求。
3. `article-guardrails.md`。
4. 当前 Review 的修改范围。
5. `style-guide.md` 和 `anti-patterns.md`。

出现以下情况必须停止，不猜测：

- 当前 Head SHA 与开始处理时不一致。
- 修改意见要求改变来源已经固定的事实。
- 无法区分正文与代码、引用或人工区域。
- 缺少支撑版本、API、兼容性或性能结论的来源。
- 修改会越过本轮授权章节。
- Skill 的必需 reference 缺失。

停止时说明具体冲突、受影响位置和需要人工决定的问题，不提交或覆盖远端更新。

## 9. 确定性校验

继续使用：

```sh
article-hub validate article \
  --article-file <article.md> \
  --config config/projects.yml
```

Draft PR 更新和 Issue 状态回写沿用现有命令，不在本次设计中改变 CLI 行为。

## 10. 测试策略

### 10.1 结构测试

更新 `tests/integration/polish-skill.test.ts`，验证：

- `SKILL.md` 和四个 reference 文件存在。
- 不存在 `LICENSE.shuorenhua`。
- 不存在 `references/shuorenhua/`。
- `SKILL.md` 不引用嵌套 Skill、上游仓库或固定 Commit。
- 所有本地 reference 链接都指向存在的文件。
- `SKILL.md` 包含三种输入场景、Head SHA 保护和文章校验命令。

### 10.2 契约测试

静态检查关键保护项至少覆盖：

- YAML Front Matter。
- 代码块和行内代码。
- API、参数、版本号和 Commit SHA。
- 图片路径、链接目标、Mermaid 和 SVG。
- 不新增事实、数据、来源或能力承诺。
- 局部修订不得越过本轮范围。

静态测试只验证 Skill 是否声明这些约束，不把自然语言行为误当成完全确定性的代码功能。

### 10.3 Forward test

使用新的 Agent 上下文执行至少四组代表性任务：

1. 含 Front Matter、代码块、API、链接和版本号的技术文章。
2. 含空泛营销表达但没有可补充数据的产品介绍。
3. 含事故复盘和性能数字的长篇技术文章。
4. 只要求修改一个段落的 Draft PR Review。

每组按以下标准人工复核：

- 保真：受保护内容和事实关系未变化。
- 范围：没有修改未授权区域。
- 自然：主要模板感和空话已清理。
- 可发布：无需再次整体润色。

若 Agent 只有在看到预期答案时才能通过，应收紧 Skill 规则或测试输入，不能把答案泄漏给测试上下文。

## 11. 迁移范围

实施时只处理与本设计直接相关的文件：

- 重写 `skills/polish-opentiny-article/SKILL.md`。
- 删除 `skills/polish-opentiny-article/references/shuorenhua/`。
- 不创建 `LICENSE.shuorenhua` 或 `SOURCE.md`。
- 将现有保护边界整理为 `references/article-guardrails.md`。
- 新增其余三个本地 reference。
- 更新 `docs/article-generation-requirements.md` 中的 Skill 结构和职责说明。
- 更新 `tests/integration/polish-skill.test.ts`。
- 按需要更新只与旧术语相关的结构或术语测试。

不修改 CLI 命令行为、文章 schema、项目配置、GitHub 模板或生成 Skill 的其他流程。

## 12. 验收标准

- 仓库运行材料中不再存在 `shuorenhua`、其 License、来源仓库或固定 Commit 依赖。
- `polish-opentiny-article` 是唯一文章优化 Skill，且没有嵌套子 Skill。
- Skill 只包含 OpenTiny 技术文章需要的规则和示例。
- 初稿全文优化、全文润色和局部修订的边界明确且不互相冲突。
- 事实、术语、代码、Front Matter、链接和图表源内容有明确保护规则。
- 无来源信息不会被改写成更确定的事实，也不会通过虚构细节补全。
- `article-hub validate article` 仍是提交前的确定性门槛。
- 相关自动化测试通过。
- 四组 forward test 均满足保真、范围、自然和可发布要求。
