# TinyRobot 组件文档规范

## 1. 目的与适用范围

本规范用于指导 TinyRobot 组件文档的编写、评审和维护，目标是让读者能够先快速完成首次使用，再按需理解状态、交互、组合方式和完整 API。

本规范适用于：

- 新增组件的正式文档；
- 对既有组件文档的实质性修改；
- 复合组件、命名空间子组件及可独立使用的组件原语；
- 与组件公开行为直接相关的 Demo、API 表格和迁移说明。

既有文档不要求一次性重写。修改某个组件时，应在当前改动范围内逐步向本规范靠拢。Composable 和工具类可以复用本文的渐进式表达、示例质量和 API 准确性原则，但不强制套用完整组件页面结构。

“实质性修改”包括新增或删除公开 API、重组主要用法或 API 章节、替换关键 Demo，以及改变状态、交互或职责边界的说明。这类修改 MUST 审计当前页面涉及的完整公开契约。只修正错别字、失效链接或不改变含义的局部措辞时，不强制顺带重写整页，但仍不得保留当前改动直接触及的已知错误。

本规范不负责：

- 设计或约束非正式的本地预览、探索和验证工具；
- 要求组件页提供外部文献、参考链接或相关页面链接清单；
- 设计或调整一般性的 VitePress 侧边栏、文档导航或站点信息架构；公开入口的弃用状态发生变化时，仍必须按第 10 节检查首屏、导航标签和推荐链接是否保持一致；
- 直接新增或修改 CI 门禁。本文只记录作者和评审者应执行的验证责任。

本文使用以下规范词：

- **MUST**：必须满足；不满足时不能认为文档已经完成。
- **SHOULD**：通常应满足；省略时应有明确的组件特性或范围理由。
- **MAY**：按组件复杂度和读者需要选择。

## 2. 核心原则

### 2.1 先帮助使用，再提供参考

组件页应同时服务两类任务：

1. 让首次使用者在最短时间内完成正确接入；
2. 让已有使用者快速查到行为边界和完整 API。

因此，正文必须先给出定位，并在 API 之前提供一个满足 L0 的基础示例，再按组件实际任务逐步进入状态、交互、组合和高级能力，最后提供完整 API。这里约束的是学习顺序和内容深度，不要求页面显示固定的章节名称。不要用一张 API 表替代教学，也不要用 Demo 画廊替代精确契约。

### 2.2 示例解释行为，API 覆盖契约

- Demo 负责回答“怎么用”“用户会看到什么”“多个接口如何协同”。
- API 表负责回答“公开接口有哪些”“类型、默认值和责任边界是什么”。
- 所有公开 API 都必须进入对应 API 表，但不是每个 Prop 都需要独立 Demo。

### 2.3 一个 Demo 只解决一个主要问题

一个 Demo MUST 有且只有一个主要学习目标。它可以包含支撑该目标的必要状态，但不能同时承担尺寸、主题、插槽、远程请求、权限和复杂布局等多个无关目标。

综合 Playground MAY 存在，但不能替代分层示例。

### 2.4 按问题选择事实源

正式组件文档 MUST 与当前公开 API 和运行时行为一致，但不同问题的事实源不同，不应使用一条固定的全局优先级覆盖所有判断。

| 要确认的问题                            | 首要事实源                                                      | 辅助事实源                       |
| --------------------------------------- | --------------------------------------------------------------- | -------------------------------- |
| 组件、类型是否从公共入口导出            | 包根导出、显式公共导出文件                                      | 组件目录导出                     |
| Props、Events、Slots 的 TypeScript 契约 | 公开 TypeScript 类型                                            | 实现、类型测试                   |
| 默认值、优先级和运行时行为              | 实际实现                                                        | 稳定行为测试                     |
| 用户交互是否属于稳定行为                | 实际实现和稳定行为测试                                          | 架构约束                         |
| 组件、宿主和子组件的职责边界            | 公开 API 和架构约束                                             | 实际实现                         |
| Demo 和正文是否准确                     | 上述对应事实源                                                  | 既有文档和 Demo                  |
| CSS Variable 是否属于公共接口           | 项目的公共主题 / token 契约、显式公共声明或已确认的公共设计决定 | 实际实现用于核对默认值和作用范围 |

作者 MUST 先确认“是否公开”，再描述“如何工作”。内部实现中存在的组件、类型、DOM、CSS Variable 或辅助状态不能仅因为可以观察到就写成公共 API；既有文档和 Demo 也不能反向证明某项能力真实存在。

尚未实现、尚未公开或尚未发布的预期 API 应记录在设计文档中，不能提前写入正式组件文档。事实源之间出现冲突时，必须按当前问题的类别回到对应首要事实源核对，而不是复制旧文档后做推断。

### 2.5 示例必须可运行、确定且可恢复

正式行为示例 MUST 使用 TinyRobot 当前文档工具链：

- Demo 文件放在 `docs/demos/<component>/`；
- 组件页面放在 `docs/src/components/`；
- 页面通过 `<demo>` 引入可运行示例。

示例不得依赖不可控的真实后端、随机数据、当前时间、登录态或不稳定远程资源。异步场景应使用确定性本地 mock，并提供可重复触发和恢复的方式。

### 2.6 简体中文优先与角色称谓

正式中文文档 MUST 首先符合现代简体中文的自然表达，再考虑英文术语或源码命名的对应关系。API 名、类型名和通行技术术语可以保留英文，但正文不应为了逐字对应英文而使用生硬直译、内部组织术语或不必要的抽象名词。

描述角色和责任时，SHOULD 根据实际关系选择称谓，而不是用一个词泛指所有组件接入者：

| 称谓        | 适用场景                                         | 使用原则                                                                    |
| ----------- | ------------------------------------------------ | --------------------------------------------------------------------------- |
| 用户        | 实际操作界面的最终用户                           | 只描述用户可见、可操作的行为，不用于指代编写代码的人                        |
| 开发者      | 阅读文档、接入或定制组件的人                     | 面向读者给出说明、限制和建议时优先使用                                      |
| 应用        | 组件外部持有数据、处理事件或决定后续界面的代码   | 描述状态更新、持久化、请求和页面跳转等外部责任时优先使用                    |
| 父组件      | Vue 组件树中真实存在的父子关系                   | 仅在 `v-model`、受控 Prop 更新、Provide/Inject 等父子关系本身影响行为时使用 |
| 宿主 / 容器 | 承载组件的页面、Dialog、Drawer 或其他界面容器    | 仅在定位、焦点、滚动、遮罩等容器职责需要区分时使用                          |
| 调用方      | 调用函数、Composable、Method 或命令式 API 的代码 | 更适合非组件式 API，不作为组件文档中的默认角色称谓                          |
| 组件使用者  | 需要泛指公共 API 使用者且无法进一步明确角色时    | SHOULD 少用；能够明确为“开发者”“应用”或“父组件”时优先使用更具体的称谓       |

`业务方`、`消费方`、`消费者` 等称谓不应作为组件文档中的默认角色名称：它们可能带入特定组织分工、业务开发假设或英文 `consumer` 的直译语感。只有在确实讨论特定业务领域与通用组件的边界时，才使用“业务”描述该领域本身，并优先写成“具体应用逻辑”“领域逻辑”等能够说明实际含义的词语。

同样地，`业务代码`、`业务数据`、`业务事件` 不应作为无差别的通用术语。应根据语义改为“应用代码”“外部数据”“用户操作事件”“值更新事件”“组件事件”等更准确的表达。例如：

- 不推荐：“业务方收到 `action` 后更新数据。”
- 推荐：“应用收到 `action` 后更新数据。”
- 不推荐：“消费者需要同步 `model-value`。”
- 推荐：“受控模式下，父组件需要更新 `model-value`。”
- 不推荐：“业务代码根据 `name-click` 打开详情。”
- 推荐：“应用根据 `name-click` 决定如何打开详情。”

行文 SHOULD 使用短句和明确主语，优先直接说明“谁做什么、何时发生、结果是什么”。避免“进行……处理”“相关能力”“业务侧”“消费侧”等可以被更具体表达替代的空泛措辞。

## 3. 文档复杂度分级

组件复杂度决定教学深度，不影响 API 完整性。

| 等级 | 典型组件                             | 最低教学深度     | 说明                                 |
| ---- | ------------------------------------ | ---------------- | ------------------------------------ |
| 简单 | 展示型组件、单一交互原语             | L0；L1/L2 按需   | 不为凑结构创建空章节                 |
| 标准 | 有多个常用变体、状态或事件的组件     | 至少覆盖到 L3    | 需要解释状态与应用接入方式           |
| 复杂 | 复合组件、状态管理组件、布局或管理器 | 按需覆盖到 L4/L5 | 需要解释职责边界、组合方式和高级限制 |

作者在开始写文档前 SHOULD 先判断组件等级。若在编写过程中发现组件包含受控状态、多层组合或复杂副作用，应提升等级并补足相应说明。

## 4. 标准页面结构

组件页采用“少量大章节 + 面向任务的小章节”。L0～L5 是作者和评审者判断内容深度、覆盖范围与排列顺序的内部等级，不是必须展示给读者的固定标题。简单组件可以省略不适用的小章节，但不得保留空标题。

未包含独立接入流程的简单或标准组件，推荐使用下面的结构：

```text
# 组件名

## 概览
### 适用场景
### 选择建议（按需）

## 用法示例
满足 L0 的基础 Demo，不额外创建同义子标题
### <按用户任务命名的核心能力>
#### <核心能力下的场景或变体（按需）>
### 综合 Playground（可选）

## 可访问性与设计约束（按需）
### 键盘与焦点
### 响应式与长内容
### 主题与 CSS 变量

## API
### Props
### Events
### Slots
### Methods / Expose
### Types
### CSS Variables

## 迁移与弃用（按需）
## 常见问题（按需）
```

只有首次成功需要安装、Provider、初始化对象、外部服务或多个连续步骤时，页面才 SHOULD 在“用法示例”之前建立独立的“快速开始”，并按真实接入步骤组织内容，例如：

```text
## 快速开始
### 前置条件或安装
### 初始化
### 完成第一次操作

## 常见任务
## API
```

上面的章节名称是组织示例，不是必须原样复制的标题。`状态与反馈`、`交互与状态管理`、`组合与定制` 等名称也只表示推荐内容维度；正式页面 SHOULD 根据组件的真实任务改为更具体的标题。

### 4.1 Frontmatter 与标题

组件页 SHOULD 使用与现有组件文档一致的 frontmatter：

```yaml
---
outline: [1, 3]
---
```

标题使用 `# EnglishName 中文名称`。正文中的组件名、类型名和代码标识符保留源码大小写。

### 4.2 概览

概览 MUST 用一到两句话说明：

- 组件解决什么问题；
- 它面向什么使用场景；
- 它是独立组件、组合原语还是特定领域适配入口。

每个组件 MUST 有清晰的“适用场景”。“不使用场景”不是固定章节；当组件容易与其他组件混淆、存在明显限制或需要宿主承担关键职责时，SHOULD 使用“选择建议”说明边界。

首个 L0 Demo 之前的概览和“选择建议”MUST 用用户任务、可见能力和组件职责给出选择结论，不得在此枚举或展开具体 Props、Events、Slots、类型及状态同步机制。相关字段、事件、插槽和状态归属 SHOULD 放在 L0 后的任务章节或 API。安装前置、弃用警告或直接影响选型的关键限制确需提前出现时，MAY 提及必要的公开标识符，但 MUST 同时解释它对读者的意义。

例如，内容管理组件需要说明自己是否拥有 Dialog、Drawer、焦点陷阱或持久化责任；用途显而易见的简单展示组件无需硬写“不适用场景”。

### 4.3 基础示例与快速开始

每个组件页 MUST 在 API 之前提供一个满足 L0 的基础示例。L0 是内容深度和验收等级，不要求显示为“最小可运行示例”，也不要求放在名为“快速开始”的章节中。简单和标准组件 SHOULD 将 L0 作为示例区的第一项，并按用户任务命名为“基础用法”或更具体的场景。

只有首次成功需要安装、Provider、初始化对象、外部服务或多个连续步骤时，页面才 SHOULD 建立独立的“快速开始”。如果一个章节只有一个子章节，并且两者语义相同，SHOULD 合并层级。

L0 中的“最小”指在完整表达一个典型使用需求的前提下，移除与主要目标无关的内容，而不是追求代码行数、Prop 数量或数据条目数最少。删除任一剩余内容后，如果读者无法识别组件的核心结构、完成主要操作或观察操作结果，该内容就不应删除。

- 仅保留完成该典型使用需求所需的 import、数据、状态、事件处理和模板；
- 示例数据 MUST 是能够体现组件核心结构与关系的最小代表性数据集；
- 列表、网格、分组等集合类组件 SHOULD 使用 2～3 个语义不同的代表性条目；典型场景包含分组、对比或状态迁移时，数据还 MUST 覆盖完成主要目标所需的关系；
- 展示型组件完成渲染本身可以构成可观察结果；如果典型用途包含用户操作，主要操作 MUST 在示例内形成可观察的结果，不能留下无结果的按钮或无法保持的状态；
- 使用公开推荐组件名和 API；
- 不引入应用框架、远程接口或无关样式；
- 复制后能够独立理解，不依赖后文才能补全关键代码；
- 示例前用一句话说明结果，而不是重复标题。

单条数据仅在它仍能完整体现组件的典型用途时使用。仅用于说明空列表、单条数据等边界状态的内容，通常放在 L2 或 L5。不要为了缩短代码而删掉组件的核心使用方式，也不要把次要能力、异常分支或完整应用流程塞进 L0。

### 4.4 用法示例

用法示例按读者需要由浅入深排列。章节名称应表达用户任务或行为，不应机械地按每个 Prop 名称分章。

同一个状态由多个强相关 API 共同描述时，SHOULD 按状态或开发者任务组织内容，例如“当前选择”“当前标签页”“展开状态”，而不是按 `model-value`、`default-*` 等单个 Prop 分章。同一状态同时支持受控和非受控模式时，也 SHOULD 优先在同一小节中说明两种模式的关系；只有两种模式存在明显不同的使用流程或约束时，再拆分为独立小节。

下面是推荐的内容顺序，不是固定标题：

1. 常用变体；
2. 状态与反馈；
3. 交互与状态管理；
4. 组合与定制；
5. 高级与边界场景；
6. 综合 Playground（可选）。

#### 标题层级与拆页

标题层级取决于读者是否需要把内容作为独立导航入口，不取决于涉及的 Props 数量：

| 内容                                             | 推荐组织                    |
| ------------------------------------------------ | --------------------------- |
| 值得进入页面目录的主要任务域、核心能力或独立组件 | H3                          |
| 主要任务域下的具体场景、变体或局部约束           | H4                          |
| 多个 Props 共同完成一个任务                      | 同一任务章节中的正文或 Demo |
| 单个 Prop 的定义                                 | API 表格                    |
| 独立导出的复杂子组件                             | H3 API 分组或独立页面       |
| 拥有大量场景、API 和约束的独立能力               | 独立功能页                  |

当一个 H4 可以脱离相邻内容独立理解，并且具有多个 Demo、独立行为模型、重要限制、较高检索需求或经常需要被外部链接时，SHOULD 将其提升为 H3。当一个 H3 下只有一个 H4，且二者语义相同，SHOULD 合并层级。

当某项能力拥有独立读者、状态模型、API、迁移说明或重要边界，并且继续放在主页面会明显降低检索效率时，SHOULD 拆分为独立页面，而不是继续增加标题层级。拆页后主页面仍应保留能力定位、最小组合和稳定链接。

### 4.5 状态与反馈

“状态与反馈”回答组件在某种状态下如何呈现，适合说明：

- `loading`、`disabled`、`empty`、`error`；
- `selected`、`active`、`success` 等持续状态；
- 状态优先级、互斥关系和恢复方式；
- 异步期间哪些操作仍可用。

空状态 MUST 区分“数据源不存在可操作目标”和“筛选后暂时没有结果”等不同原因。不存在可操作、可搜索或可筛选目标时，不得保留看似可用但无法产生有效结果的控件；通常隐藏控件，仅在不可用原因需要传达时禁用并说明。筛选条件仍可用于恢复结果时，搜索或筛选控件应继续可用。

不要把静态状态展示和外部数据同步混在同一个示例中。

### 4.6 交互与状态管理

“交互与状态管理”回答应用如何接收组件事件、更新状态并观察结果，适合说明：

- 事件触发时机与 payload；
- `v-model` 或 `update:*`；
- 受控与非受控边界；
- 异步操作、取消、重试；
- 键盘操作和焦点移动；
- 父组件更新数据源的责任。

状态与交互默认作为“用法示例”下的两个平级小章节。复杂组件内容较多时，MAY 将它们提升为独立大章节。

复杂组件如果同时包含外部数据源、受控值、非受控内部状态或临时 UI 状态中的两类以上，MUST 明确状态所有权。状态所有权不固定使用表格或列表，应根据内容选择结构：

- 重点是比较多项状态由谁管理，并且单元格可以使用简短短语表达时，MAY 使用两到三列摘要表格。表格只保留“状态 / 数据”“管理方”“更新方式”等便于扫描的信息；
- 涉及初始值、事件顺序、条件分支、回退规则或多个 API 的配合方式时，MUST 使用纵向分组或短段落补充说明；
- 不要把完整状态转换过程压缩进宽表格，也不要只描述事件名称而不说明谁真正更新数据。

- **示例受控值**：值来自 `model-value`，由父组件管理。用户操作后，父组件收到 `update:model-value` 并更新绑定值。
- **示例展开状态**：初始值来自组件默认配置，由组件管理。用户操作后，组件更新内部状态并触发 `toggle`。

同一状态维度同时支持受控和非受控模式时，MUST 区分两种模式下的值来源、初始值、更新责任、更新事件和回退规则，但默认 SHOULD 合并在以该状态命名的同一小节中说明。内容较多时，优先按受控方式和非受控方式纵向分组；不要仅因为存在两种控制模式，就建立内容重复的镜像小节。

只有两种模式在交互流程、可用 API、异步责任或适用场景上存在明显差异，并且分别说明能显著降低理解成本时，才 SHOULD 拆成独立小节或 Demo。同一个事件在两种模式下责任不同的，MUST 明确责任差异，但不要求为此拆成独立章节。

不要把组件已经更新内部状态后的通知事件写成“父组件必须更新绑定值”，也不要把只表示用户操作的受控事件写成“组件已经修改外部数据”。

### 4.7 综合 Playground

综合 Playground MAY 放在所有渐进示例之后、API 之前，用于集中探索多个可调参数。它必须满足：

- 页面已有 L0 和关键分层示例；
- 不被称为“基础用法”或唯一示例；
- 默认配置代表推荐用法；
- 控件按概念分组，不暴露内部实现细节；
- 可以恢复初始状态；
- 不依赖真实外部服务。

页面顶部 MAY 展示简洁效果预览，但不应把包含大量开关的综合 Playground 放在首屏作为学习入口。

## 5. Demo 渐进模型

L0～L5 用于规划覆盖深度和检查学习路径，不要求出现在页面标题、Demo 标题或导航中。复杂组件 SHOULD 先按用户任务划分能力域，再在各能力域内由浅入深安排适用的 Demo。

| 级别              | 读者问题               | Demo 重点                            | 最低要求                     |
| ----------------- | ---------------------- | ------------------------------------ | ---------------------------- |
| L0 基础用法       | 如何完成首次接入？     | 满足典型使用需求的最小代表性闭环     | 可复制、结构可辨、结果可见   |
| L1 常用变体       | 日常最常改什么？       | 常用 variant、size、布局等           | 一组强相关变量，可直接比较   |
| L2 状态与反馈     | 不同状态下会看到什么？ | loading、disabled、empty、error 等   | 说明状态优先级与可操作性     |
| L3 交互与状态管理 | 应用如何接入？         | event、`v-model`、受控更新、异步行为 | 结果可见，责任边界明确       |
| L4 组合与定制     | 如何嵌入真实界面？     | slot、相邻组件、命名空间子组件       | 只引入完成组合所需的依赖     |
| L5 高级与边界     | 极端或高级需求怎么办？ | 响应式、长内容、主题、性能、复杂边界 | 明确限制、稳定入口和适用条件 |

### 5.1 停止规则

不是每个组件都要写到 L5：

- 简单组件至少提供 L0，存在常见变体或关键状态时补 L1/L2；
- 标准组件通常写到 L3；
- 复杂组件根据公开能力写到 L4/L5；
- 没有对应能力时直接停止，不创建“暂无”Demo；
- API 表始终保持完整。

### 5.2 Props 的 Demo 选择

对公开 Prop 按行为影响分类：

| 类别        | 判断标准                             | 最低文档要求                  |
| ----------- | ------------------------------------ | ----------------------------- |
| A：关键行为 | 改变结构、交互、状态所有权或数据流   | MUST：正文 + Demo + API       |
| B：常用变体 | 高频视觉或布局选择，多个值适合比较   | SHOULD：正文或对比 Demo + API |
| C：直接配置 | 含义直观、风险低、无需与其他接口联动 | MUST：API；正文和 Demo 按需   |

同一个 Demo 可以覆盖多个强相关 Prop，但必须仍然只有一个主要学习目标。例如，`size` 的多个可选值可以放在一个尺寸对比 Demo 中；`loading` 与异步提交责任不应因为都涉及按钮而强行塞进同一个示例。

评审时 MUST 先为每个公开 Prop 归类，再检查它是否满足对应最低要求。由于所有公开 Prop 本来就必须进入 Props API 表，不能再使用“Demo、正文或 API 任意出现一处”作为完成条件，否则 C 类最低要求会掩盖 A 类关键行为缺少教学说明的问题。

### 5.3 Demo 的保留、合并与拆分

多个 Demo 的代码设置相似，不代表它们应该合并；判断依据是学习目标、前置知识和可观察结果：

| 情况                         | 处理方式             |
| ---------------------------- | -------------------- |
| 学习目标和可观察结果相同     | 合并或删除重复 Demo  |
| 同一概念的多个值适合直接比较 | 合并为对比 Demo      |
| 前置知识、用户任务或结果不同 | 保持独立 Demo        |
| 合并后出现多个无关主要目标   | 拆分 Demo            |
| 只是初始化代码重复           | 不能单独作为合并理由 |

Demo 调整后仍需保证页面从基础用法到高级场景的学习顺序连续，不因删除重复内容而丢失必要的中间步骤。

## 6. Demo 编写规范

### 6.1 文件位置与命名

新 Demo MUST 放在：

```text
docs/demos/<component>/<purpose>.vue
```

推荐使用 kebab-case 和行为语义命名，例如：

```text
docs/demos/model-selector/basic.vue
docs/demos/model-selector/loading.vue
docs/demos/model-selector/controlled-selection.vue
docs/demos/model-selector/custom-trigger.vue
```

以上路径用于展示命名模式，不表示仓库当前已经存在这些文件。正式文档只能引用已经创建并验证的 Demo。

不要使用 `demo1.vue`、`test.vue`、`new.vue` 或只描述实现方式的文件名。

### 6.2 页面引入

标准和复杂组件的 Demo SHOULD 显式提供 `title` 和 `description`：

```html
<demo
  vue="../../demos/<component>/controlled-selection.vue"
  title="受控选择"
  description="由父组件持有当前模型，并在选择事件后同步状态。"
/>
```

上面的 `<component>` 是规范中的路径占位符，使用时必须替换为真实组件目录和已经创建的 Demo 文件。

非常简单且紧邻明确正文的 L0 Demo MAY 只写：

```html
<demo vue="../../demos/prompts/basic.vue" />
```

`title` 应说明场景，`description` 应说明结果或适用时机，不要重复标题或写“这是一个示例”。

### 6.3 多文件 Demo

当示例必须拆出类型、mock 数据或样式时，将相关文件放在同一 Demo 目录，并使用 `:vueFiles` 明确展示：

```html
<demo
  vue="../../demos/example/async-state.vue"
  :vueFiles="[
    '../../demos/example/async-state.vue',
    '../../demos/example/mock-data.ts',
  ]"
  title="异步状态"
  description="使用确定性本地数据演示加载、成功与失败反馈。"
/>
```

只有理解主要示例所必需的文件才能进入 `vueFiles`。纯测试夹具、生成文件和无关工具不得展示给读者。

### 6.4 组件导入与模板标签

Demo MUST 遵循 TinyRobot 现有导出约定：

```vue
<script setup lang="ts">
import { TrPrompts } from '@opentiny/tiny-robot'
import type { PromptProps } from '@opentiny/tiny-robot'
</script>

<template>
  <tr-prompts :items="items" />
</template>
```

- 按需导入带 `Tr` 前缀的组件；
- TypeScript 类型使用 `import type`；
- 模板标签使用带 `tr-` 前缀的 kebab-case；
- 不展示内部路径导入；
- 不用非公开组件或私有类型完成正式 Demo。

### 6.5 数据与副作用

所有 Demo MUST：

- 使用含义明确、数量适中的本地数据；
- 保证刷新后初始状态一致；
- 让事件或异步结果在界面中可观察；
- 在组件卸载时清理监听器、计时器和对象 URL；

“可观察”表示读者无需打开开发者工具即可在当前示例中看到结果。展示型组件完成预期渲染即可；事件、异步操作、错误或取消场景则应在示例内展示相应状态。主要结果 MUST 可以重复触发，并能够恢复到可继续操作的状态；控制台日志、浏览器弹窗或不可见的内部状态不能作为唯一结果。

涉及异步、loading 或 error 的 Demo 还 MUST：

- 为加载、成功、失败提供可重复触发的入口；
- 避免自动执行不可逆操作。

Demo SHOULD 避免：

- 依赖公网请求或远程图片；
- 使用 `Math.random()` 或当前时间生成关键内容；
- 使用只能触发一次、无法恢复的状态；
- 为了视觉丰富引入与学习目标无关的布局；
- 用控制台输出作为用户唯一能观察到的结果。

### 6.6 可运行 Demo 与集成参考代码

真实服务集成涉及浏览器权限、服务端代理、鉴权、WebSocket 或私有凭据时，可以保留有价值的集成参考，但必须与正式可运行 Demo 区分：

| 产物         | 用途                                 | 要求                                                                                     |
| ------------ | ------------------------------------ | ---------------------------------------------------------------------------------------- |
| 可运行 Demo  | 证明组件公开行为和主要交互           | 使用确定性本地数据或 mock；可重复触发和恢复；不得依赖私有凭据或不可控服务                |
| 集成参考代码 | 解释接入真实服务所需的职责和调用形态 | 明确标记为参考；列出权限、代理、鉴权、凭据保护和失败处理责任；不得暗示复制后即可直接运行 |

主学习路径 MUST 使用可运行 Demo。集成参考代码 MAY 放在高级或边界章节，但不能替代对应的本地行为示例，也不能把密钥、令牌或应在服务端完成的签名逻辑放入浏览器代码。

### 6.7 内联代码

Markdown 内联代码 MAY 用于：

- 展示 import；
- 展示一个很短的类型或调用片段；
- 解释无需运行的局部语法。

承担行为证明、交互说明或状态演示的代码 MUST 放入 `docs/demos/` 并通过 `<demo>` 引入。

## 7. API 编写规范

API 必须来自当前公开类型和实现。作者在提交前应逐项核对源码，而不是复制旧文档后只修改标题。

### 7.1 Props

| 属性名        | 说明                                     | 类型      | 默认值  | 必填 |
| ------------- | ---------------------------------------- | --------- | ------- | ---- |
| `model-value` | 当前受控值；父组件收到更新事件后更新该值 | `string`  | —       | 是   |
| `disabled`    | 是否禁用用户操作                         | `boolean` | `false` | 否   |

要求：

- 属性名使用模板中的 kebab-case；
- 说明必须描述行为、限制和联动，不重复类型；
- 默认值 SHOULD 写组件实际生效的默认行为，而不是只写“继承子组件默认值”或内部实现占位；若默认值经过条目级配置、父组件配置、Provider 或子组件 fallback 链得到，说明中 MUST 写清优先级，例如 `item.prop > collection.prop > child default`；
- 没有默认值时使用 `—`，不要写 `undefined` 代替未定义契约；没有固定有效默认值时可以写由哪个公开输入决定，但必须说明决策规则；
- 联合类型较长时可以引用 Types 小节中的公开类型名；
- 受控 Prop 必须说明父组件更新责任，并说明与对应 `default-*` Prop 同时提供时的优先级和实际行为。

### 7.2 Events

面向读者的 API 章节统一使用 `Events`。只有解释 Vue 选项、公开类型名称或实现签名时，才使用 `emits` 或 `Emits`。

| 事件名               | 触发时机             | 回调参数                                         |
| -------------------- | -------------------- | ------------------------------------------------ |
| `update:model-value` | 用户确认新值时       | `(value: string) => void`                        |
| `change`             | 已完成一次有效选择时 | `(value: string, previousValue: string) => void` |

要求：

- 区分用户操作事件、值更新事件和生命周期通知；
- 说明事件在校验前还是校验后触发；
- 给出完整 payload 类型和参数顺序；
- 涉及状态变化的事件 MUST 说明事件发出时组件是否已经更新内部状态，还是仅提供下一状态；
- 涉及外部数据或受控值的事件 MUST 说明应用通常需要更新数据、执行副作用，还是无需处理；
- 同一事件在受控和非受控模式下责任不同的，MUST 明确区分两种模式下的责任差异，但不要求拆成独立章节；
- 若事件不会自动修改受控值，必须明确说明。

事件 API 若采用表格，只保留“事件名 / 触发时机 / 回调参数”三列。复杂状态事件需要补充状态副作用或后续处理时，SHOULD 在表格前后使用纵向分组或短段落说明，避免继续增加横向列。

### 7.3 Slots

| 插槽名    | 用途           | 作用域参数                      |
| --------- | -------------- | ------------------------------- |
| `default` | 自定义主体内容 | `{ item: Item; index: number }` |
| `empty`   | 自定义空状态   | `—`                             |

要求：

- 说明插槽替换或扩展哪个区域；
- 列出完整作用域参数；
- 说明与对应 Prop 同时提供时的优先级；
- 如果插槽替换默认交互子树，MUST 说明默认事件转发、键盘行为、ARIA、焦点或内部状态是否仍然保留，以及哪些责任需要由插槽内容或开发者自行承担；
- 作用域提供 `trigger()`、`select()`、`close()` 等稳定回调以保留默认行为时，SHOULD 明确推荐通过这些回调接入，而不是依赖内部 DOM；
- 不鼓励依赖内部 DOM 结构的定制方式。

### 7.4 Methods / Expose

| 方法名  | 说明                       | 签名         |
| ------- | -------------------------- | ------------ |
| `focus` | 将焦点移入组件的主交互入口 | `() => void` |

方法说明 MUST 包含参数、返回值和可见副作用。没有公开方法时省略该小节，不写空表。

### 7.5 Types

Types 采用“完整索引 + 选择性定义”。与当前页面记录的组件、子组件和公开扩展直接相关的所有公开类型 MUST 先进入 Types 索引表，保证读者可以按公开名称查找。页面 SHOULD 先说明默认从 `@opentiny/tiny-robot` 导入；全部类型使用同一路径时，不在每一行重复导入信息：

| 类型名        | 类型或签名  | 说明                 |
| ------------- | ----------- | -------------------- |
| `ExampleItem` | `interface` | 组件接收的单个数据项 |

只有页面存在多个公开导入路径时，索引表才增加“导入路径”列，并填写开发者实际用于 `import` 的公共路径，不使用“导出入口”作为列名。

复杂公开类型 MAY 在索引表之后选择性展开 TypeScript 定义，再对非直观字段增加字段表。每个连续代码块之前 MUST 明确标记它是“完整定义”还是“片段”，并说明覆盖范围。声明为完整定义时，必须覆盖所声称范围内的全部公开类型和字段；声明为片段时，只能省略与当前说明目标无关的部分，并明确省略内容由哪个 API 表或事实源覆盖。

以下为 `ExampleItem` 的完整定义：

```ts
interface ExampleItem {
  id: string
  label: string
  disabled?: boolean
}
```

| 字段       | 说明                 | 类型      | 必填 |
| ---------- | -------------------- | --------- | ---- |
| `id`       | 稳定且唯一的条目标识 | `string`  | 是   |
| `label`    | 展示文本             | `string`  | 是   |
| `disabled` | 是否禁止用户选择     | `boolean` | 否   |

Props、Events 和 Slots 已经由专门 API 表完整说明时，不要求在 Types 代码块中再次复制整套声明。不要在文档中重新设计一份与源码不同的“简化类型”，也不要让选择性展开的代码块看起来像全部公开定义。

#### 7.5.1 核心对象型 Prop

当 `data`、`ui`、`options`、`config`、`schema` 等对象型 Prop 构成组件的主要数据模型或配置模型，并包含多个直接影响可见区域、状态所有权或默认行为的分支时，不能只在 Types 索引中列出字段签名。页面 MUST 先给出一级字段到界面区域或职责的结构概览，让开发者能够判断数据、配置和交互状态分别由谁管理。

核心对象型 Prop 的详细说明 MUST 覆盖：

- 每个一级字段的用途、类型、必填性，以及它影响的可见区域或行为；
- 字段省略、传入 `undefined`、`false`、空对象或空集合时的实际结果；
- 实际生效的默认值、逐层 fallback、对象合并或整体替换规则；
- 与受控 Props、默认值 Props、Provider、Runtime、Slots 或子组件配置同时存在时的优先级和状态所有权；
- 多个字段必须配合使用时的依赖关系、互斥条件和恢复方式。

如果对象控制多个可见区域或关键交互，页面 MUST 提供最小代表性 Demo，展示一组语义完整的数据或配置如何映射到界面。数据模型和界面配置具有不同学习目标时，SHOULD 使用独立 Demo；不要把一组互不相关的布尔状态开关当成对象结构说明。

字段较多时，MAY 按职责拆成多张纵向表格或独立参考页。拆页后主页面仍 MUST 保留职责概览、最小完整对象、常用字段说明和稳定链接。`field?: Type` 形式的扁平签名列表只构成类型索引，不能替代上述行为说明。

#### 7.5.2 Composable 与 Runtime API

当 Composable 或 Runtime 是页面的主要公开入口时，页面 MUST 说明它解决的任务、适用条件和状态所有权，不能只列函数签名。存在多个工厂或适配入口时，MUST 给出选择关系，并比较它们创建、复用或适配哪些状态，以及分别安装哪些默认能力。

配置对象的说明 MUST 覆盖必填性、默认值、响应式输入形态、读取时机、合并或替换规则、互斥条件和外部资源责任。接受普通值、Ref 或 Getter 时，必须说明哪些变化会被持续跟踪；只在初始化时读取的配置也必须明确。

返回对象 SHOULD 按“状态 / 派生状态 / 动作”分组。每个状态需要说明是否只读、是否为 Ref 或结构化可读值，以及由谁更新；每个动作需要说明参数、返回值、拒绝或短路条件、错误传播、可见副作用，以及适用时的取消、并发和清理行为。不要为了文档方便发明源码未公开的命名返回类型。

适配器连接外部状态与界面时，MUST 说明双方各自拥有的数据、事件和副作用。多个返回字段必须协同才能完成主要任务时，页面 MUST 提供最小可运行示例；示例应让异步状态、错误、取消或状态切换结果可观察。

这些规则参考 [Vue Composables](https://vuejs.org/guide/reusability/composables)、[VueUse Guidelines](https://vueuse.org/guidelines)、[assistant-ui External Store Runtime](https://www.assistant-ui.com/docs/runtimes/custom/external-store) 和 [AI SDK `useChat`](https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-chat) 对响应式输入、外部状态、适配责任和异步动作的处理，实际文档仍以 TinyRobot 的公开 API 与实现为准。

### 7.6 CSS Variables

| 变量名            | 说明           | 默认值                           |
| ----------------- | -------------- | -------------------------------- |
| `--tr-example-bg` | 组件容器背景色 | `var(--tr-container-bg-default)` |

要求：

- 只记录明确承诺为公共接口的变量；“源码中出现了 `var(--*)`”本身不足以证明变量属于公共 API；
- 公共资格 MUST 能追溯到项目的公共主题 / token 契约、源码中的显式公共声明、已发布的稳定公共文档，或经过维护者确认的公共设计决定；如果无法确认，应在评审中标记待确认，而不是自行把内部变量升级为公共接口；
- 公共资格确认后，再以实际实现核对默认值、fallback 和作用范围；
- 使用语义描述，不绑定偶然的内部 DOM 层级；
- 说明作用范围或继承关系；
- 同一组尺寸变量可以分组说明，避免重复大表。

### 7.7 API 排列

API 项目按以下顺序排列：

1. 最常用或必需项；
2. 同一行为分组内的相关项；
3. 组内按名称排序。

不要为了绝对字母顺序打散 `model-value` 与 `update:model-value`、`items` 与 `item-key` 等强相关接口。同一状态由 `model-value`、`default-*`、`update:*` / `change` 等接口共同描述时，正文和 API 说明 SHOULD 将它们作为一组关系解释，避免开发者分别查到接口却仍无法判断状态所有权和优先级。

## 9. 复合组件与命名空间组件

复合组件默认集中在一个主页面中，顺序为：

1. 说明整体职责和组合关系；
2. 给出最小完整组合；
3. 分别说明可独立使用的子组件；
4. 描述父子数据流和事件路由；
5. 选择一种一致的 API 分组轴。

同一页面的 API MUST 选择以下一种主分组轴，不得在同级标题中混用：

| 分组轴       | 推荐结构                                                         | 适用条件                                            |
| ------------ | ---------------------------------------------------------------- | --------------------------------------------------- |
| API 类别优先 | Props → 主组件 / 子组件；Events → 主组件 / 子组件                | 子组件 API 较少、主要服务同一任务流、不需要独立查阅 |
| 组件优先     | 主组件 → Props / Events / Slots；子组件 → Props / Events / Slots | 子组件可独立导入和使用、拥有独立读者或 API 较多     |

作者 SHOULD 在开始编写 API 前确定主分组轴。若使用类别优先，组件名称只作为类别下的分组；若使用组件优先，每个组件下保持统一的 Props、Events、Slots、Methods / Expose 顺序。

只有满足以下条件之一时，SHOULD 为子组件拆分独立页面：

- 子组件拥有独立且不同的主要读者；
- 子组件完全脱离父组件仍是常用入口；
- 主页面已经因该子组件的用法和 API 变得难以检索；
- 子组件有独立的迁移、无障碍或复杂状态模型。

子组件或功能拆页后，主页面仍 MUST 说明它在整体组合中的职责、给出最小组合，并链接到独立页面；独立页面不能让读者重新猜测父子关系或数据流。

文档必须尊重代码中的职责边界。不要为了让 Demo 看起来完整，把宿主持有的弹窗、持久化、权限、请求或全局状态写成组件内建能力。

## 10. 迁移与弃用

弃用内容 MUST 同时说明：

- 哪个公开入口已弃用；
- 推荐替代入口；
- 最小迁移前后对照；
- 行为差异和数据迁移风险；
- 已确定时，标出计划移除版本。

弃用提示不能只藏在 API 表。若旧入口仍可能被新用户误用，应在第一个相关示例或概览中出现简短提示。

重大升级或弃用 SHOULD 使用“首屏摘要 + 文末详情”的双层结构：首屏只说明版本、影响范围、推荐替代入口和详情链接；完整 API 对照、行为差异和迁移步骤集中在“迁移与弃用”章节，避免在页面两处重复维护完整内容。

公开入口的弃用状态发生变化时，作者 MUST 检查以下位置是否仍把旧入口表现为推荐选项：

- 组件页首屏和第一个相关示例；
- 侧边栏或导航中的名称、弃用标记和描述；
- 推荐链接、相关组件入口和迁移链接。

这项检查只要求弃用状态和推荐关系保持一致，不要求在同一改动中重新设计一般性的站点导航或信息架构。

## 14. 常见反模式

### 14.1 万能 Demo

**问题：** 一个示例同时包含大量 Props、插槽、主题、请求和复杂页面布局。

**处理：** 将它拆为 L0、状态、交互和组合示例；综合版本仅作为最后的可选 Playground。

### 14.2 示例画廊替代 API

**问题：** 页面只有多个可运行示例，没有精确的 Props、Events、Slots 和 Types。

**处理：** 保留教学示例，并补齐全部公开 API 表。

### 14.3 为每个 Prop 创建 Demo

**问题：** 页面被大量低价值、重复示例淹没。

**处理：** 使用 A/B/C 分类；关键行为单独演示，强相关变体集中比较，直观配置进入 API 表。

### 14.4 不确定性示例

**问题：** Demo 依赖真实接口、随机值、当前时间或无法恢复的异步状态。

**处理：** 使用本地确定性 mock，并提供加载、成功、失败和重置入口。

### 14.5 隐藏受控责任

**问题：** 示例展示 `v-model` 或 `model-value`，但没有说明谁更新值，以及默认值和受控值的优先级；或者把同一状态机械拆成“受控模式”和“非受控模式”两个重复章节。

**处理：** 在 L3 Demo 和 API 中同时说明值所有权、更新事件和父组件更新责任。同一状态支持两种控制模式时，优先围绕状态本身合并说明，并按受控方式和非受控方式纵向分组。

### 14.6 只声明“支持无障碍”

**问题：** 没有键盘行为、焦点移动、可访问名称或动态状态播报的具体说明。

**处理：** 写出可观察行为；适用时提供键盘或焦点 Demo，并通过组件测试保护关键结果。

### 14.7 文档暴露内部实现

**问题：** 推荐开发者依赖内部 DOM、私有类型或深层选择器。

**处理：** 只记录稳定的公开组件、类型、事件、插槽和 CSS 变量。

### 14.8 无迁移路径的弃用

**问题：** API 只标记 deprecated，没有替代方案和行为差异。

**处理：** 同时给出替代入口、最小迁移示例和已确定的移除计划。

### 14.9 把最小理解为条目最少

**问题：** 列表、网格或分组组件只提供一个条目。示例虽然能够运行，却无法体现集合结构、条目差异或主要交互。

**处理：** 使用能够表达核心关系的最小代表性数据集。集合类组件通常保留 2～3 个语义不同的条目；分组、对比或状态迁移场景还应覆盖完成主要目标所需的分区或状态。单条和空列表等边界数据放在对应的状态或边界示例中。

### 14.10 把教学等级当作固定标题

**问题：** 页面机械出现“快速开始 → 最小可运行示例 → 基础用法”等同义层级，或者直接用“L2 状态与反馈”作为读者导航。

**处理：** 保留 L0～L5 作为作者侧验收模型；页面标题改为用户任务。只有存在真实接入步骤时才建立独立“快速开始”，同义的单层父子标题应合并。

### 14.11 空状态仍保留无效控件

**问题：** 数据源不存在任何可搜索、可筛选或可操作目标时，界面仍展示看似可用但不会产生有效结果的控件。

**处理：** 区分数据源为空与筛选后无结果。前者通常隐藏无效控件，或在不可用原因需要传达时禁用并说明；后者保留能够修改条件并恢复结果的搜索或筛选入口。

## 15. 编写与评审流程

### 15.1 作者流程

1. 从包根导出和显式公共导出文件确认公开组件与类型，再用公开 TypeScript 类型列出完整 API。
2. 将页面分类为组件、Composable、Runtime 或混合 API；安排示例前，盘点配置、返回状态、动作、副作用和状态所有权。
3. 根据实际实现和稳定行为测试核对默认值、优先级和运行时行为，并确认职责边界。
4. 判断组件属于简单、标准还是复杂等级。
5. 写概览和适用场景，先用用户任务、可见能力和组件职责表达 L0 前的选择结论，再编写 L0 基础示例，并确认示例数据足以体现组件的核心结构和典型操作；仅在首次成功包含多个接入步骤时建立独立“快速开始”。
6. 按用户任务规划 H3/H4；复合组件同时确定 API 分组轴和是否需要拆页。
7. 对公开 Prop 做 A/B/C 分类，规划必要 Demo。
8. 按 L1 到 L5 补充真正适用的学习层级；复杂组件同时整理状态所有权。
9. 补充 API 表和适用性矩阵中的相关内容。
10. 按第 2.4 节的事实源规则检查示例、类型、默认值、事件责任和公共 CSS Variables。
11. 运行验证并完成 PR 检查清单。

### 15.2 验证命令

纯文档改动至少运行：

```bash
pnpm build:docs
pnpm exec prettier --check docs/src/components/prompts.md docs/demos/prompts/basic.vue
git diff --check
```

上面的 Prettier 路径只是可执行示例，实际评审时必须替换为本次所有新增或修改的 Markdown、Vue、TypeScript 和 CSS 文件。`git diff --check` 用于检查已经进入 Git diff 的内容；新建但尚未跟踪的文件也必须通过 Prettier 的显式路径检查。

若文档伴随组件公开行为或类型变化，再运行：

```bash
pnpm type-check
pnpm -F tiny-robot-test type-check:ct
pnpm -F tiny-robot-test test:ct -- <对应组件测试文件>
```

聚焦测试文件参数应替换为仓库中真实存在的组件测试路径。不要用全量测试通过替代对目标 Demo 和行为的人工检查。

### 15.3 PR 检查清单

#### 页面结构

- [ ] 页面首屏用用户任务、可见能力和组件职责说明用途、适用场景和选择边界；除必要的安装前置、弃用警告或直接影响选型的关键限制外，未在 L0 前枚举具体 API 或状态同步机制。
- [ ] API 之前有满足 L0 的基础示例，并形成满足典型使用需求的最小代表性闭环；未把 L0～L5 机械写成读者标题。
- [ ] 只有存在真实的多步接入流程时才建立独立“快速开始”；不存在语义重复的父子标题。
- [ ] 章节按读者任务由浅入深排列。
- [ ] H3 用于需要独立导航的主要任务或能力，H4 用于其中的具体场景；未按单个 Prop 机械分章。
- [ ] 没有空章节或为了凑层级创建的示例。
- [ ] 复杂组件说明了宿主、父组件和子组件的职责边界。
- [ ] 复合组件选择了一致的 API 分组轴；独立能力需要拆页时，主页面仍保留定位、最小组合和链接。
- [ ] 存在多类状态来源时，已明确外部数据、受控值、非受控状态和内部 UI 状态的所有权。

#### Demo

- [ ] 每个 Demo 只有一个主要学习目标。
- [ ] Demo 使用 `docs/demos/<component>/` 和语义化文件名。
- [ ] 标准和复杂组件的 Demo 有有效的 `title` 与 `description`。
- [ ] 使用带 `Tr` 前缀的公开导入和带 `tr-` 前缀的 kebab-case 模板标签。
- [ ] 类型使用 `import type`。
- [ ] L0 使用最小代表性数据集，没有因追求代码量或条目数最少而损失组件的核心结构、主要操作或可观察结果。
- [ ] 示例数据确定、可恢复，不依赖不可控服务。
- [ ] 事件、异步结果、错误和取消反馈无需开发者工具即可观察，并且可以重复触发和恢复；控制台或弹窗不是唯一结果。
- [ ] 真实服务内容已明确区分为集成参考代码，没有替代本地可运行 Demo，也没有暴露浏览器端凭据。
- [ ] 综合 Playground 位于分层示例之后，且不是唯一示例。
- [ ] 核心对象型 Prop 控制多个可见区域或关键交互时，已有语义完整的数据或配置 Demo；不同学习目标没有混入同一组无关状态开关。
- [ ] 多个返回字段必须连接才能完成主要任务时，已提供适配器或多字段 Composable 的最小可运行示例。

#### API

- [ ] 全部公开 Props、Events、Slots、Methods、Types 和 CSS Variables 已按对应事实源核对。
- [ ] 每个公开 Prop 已完成 A/B/C 分类，并满足该类别的正文、Demo 和 API 最低要求。
- [ ] 类型、必填性、有效默认值和配置优先级与实际公开行为一致。
- [ ] 受控状态说明了值所有权、`default-*` 优先级和父组件更新责任；同一状态同时支持受控和非受控模式时，已优先合并说明，未创建无必要的镜像章节。
- [ ] 涉及状态变化的事件说明了组件是否已更新状态，以及应用通常需要做什么。
- [ ] 替换默认交互的 Slot 说明了事件、键盘、ARIA、焦点和状态责任是否需要由插槽内容或开发者自行承担。
- [ ] Types 索引覆盖与当前页面组件、子组件和公开扩展直接相关的全部公开类型；代码块已标明“完整定义”或“片段”及覆盖范围。
- [ ] 核心对象型 Prop 已说明一级字段职责、空值行为、默认与 fallback、合并规则、优先级和状态所有权；没有用扁平签名列表替代详细 API。
- [ ] 主要 Composable 与 Runtime 已说明入口选择、配置默认值与互斥关系、返回状态的响应式/只读属性、动作的返回值与错误传播，以及适用的副作用、取消和清理责任。
- [ ] 默认导入路径只在页面中说明一次；只有存在多个公共路径时才增加“导入路径”列。
- [ ] CSS Variables 有明确的公共资格依据，未把实现中的内部变量直接当成公共 API。
- [ ] API 按常用程度和行为分组排列。
- [ ] 文档没有描述尚未实现或尚未发布的 API。

#### 质量维度

- [ ] 正文符合简体中文自然表达；“用户”“开发者”“应用”“父组件”“宿主”等称谓与实际角色一致，没有用“业务方”“消费者”等词泛指组件接入者。
- [ ] 所有适用的 loading、empty、error、disabled 等状态已说明。
- [ ] 空状态区分数据源为空与筛选后无结果；周围控件仍能产生有效结果，或已隐藏、禁用并说明原因。
- [ ] 适用时记录键盘、焦点和可访问名称。
- [ ] 适用时记录窄容器、长内容、换行、截断或滚动行为。
- [ ] 适用时记录主题变量及其作用范围。
- [ ] 适用时记录浏览器 API、副作用和清理责任。
- [ ] 弃用项包含替代入口和迁移方式；首屏、导航标签和推荐链接没有继续把旧入口表现为首选项。

#### 验证

- [ ] `pnpm build:docs` 通过。
- [ ] 所有新增和修改的文档及 Demo 文件通过 Prettier 显式路径检查。
- [ ] `git diff --check` 通过。
- [ ] 涉及组件行为时，组件 type-check 和聚焦测试通过。
- [ ] 人工检查 Demo 的默认状态、关键交互和恢复路径。

## 16. 维护规则

- 公共 API 或用户可见行为改变时，MUST 在同一 PR 更新对应文档和 Demo。
- 文档只描述当前发布目标中的公开行为，不预告未实现 API。
- 修正文档时 SHOULD 顺手消除当前改动范围内的过时示例、错误类型和重复内容。
- 组件内部重构但公开行为不变时，不要求制造新的 Demo。
- 规范本身需要调整时，应优先修改规则和模板，再逐步迁移已有页面。
- 未经维护者明确标记为规范基准的既有组件页，只能作为迁移输入，不能反向证明其标题结构、API 分组或 Demo 组织符合本规范。建立基准页面时，必须先通过第 15.3 节检查清单。
- 本规范不替代组件源码、公开类型或组件测试；三者与文档共同定义用户可依赖的行为。
