TINYROBOT / CHAT ARCHITECTURE

TinyRobot Chat

从 UI Shell 到 Runtime 的聊天系统设计

分层 适配 扩展
核心定位 Chat 将聊天 UI、业务状态与模型能力分层，让同一套界面可以接入不同 Runtime。

Architecture at a glance

TrChatUI展示布局、消息、输入与控件
TrChat + Adapter连接 UI 事件与 Runtime 动作
ChatRuntime提供会话、请求和 Composer 状态
Kit / Provider / MCP负责消息引擎、模型请求和外部工具
01

先解决两个痛点

Chat 的起点不是“再做一个聊天页面”，而是收敛已经发生的重复建设和升级成本。

Pain 01 / Version drift

版本迭代快，存量应用跟不上

GuiChat、RemoterChat 等产品依赖的 Chat 版本并不一致，部分应用仍停留在 0.3.3。版本差异带来接入方式、会话配置和请求能力的分叉，公共能力难以同步升级。

Pain 02 / No common path

没有统一的 Chat 应用标准

不同应用分别实现输入、会话、流式响应、模型切换、MCP、错误处理和窗口形态；同样的 Chat 能力没有统一入口，业务代码重复且行为不一致。

要解决的不是 UI 复用率，而是演进的一致性：让新应用有标准入口，让存量应用有迁移目标，让产品差异留在 Chat 之上。
02

基础包解决能力，Chat 解决组装，案例验证形态，CLI 负责把标准交付出去。

Foundation

components + kit

components 提供 Bubble、Sender、Layout 等交互基础；kit 提供消息引擎、会话、存储、插件和 Provider 基础协议。

Assembly

Chat

提供 TrChat、TrChatUI、ChatRuntime 和 Adapter，把基础能力组装成可接入的 Chat 应用层。

Delivery

CLI

把 Chat 的标准实现沉淀为 create 和 add chat 两条工程入口，降低新项目和存量项目的接入成本。

03

为什么这样设计

核心不是把功能堆在一个组件里，而是让每一层只对自己负责。

01

UI 与 Runtime 分离

UI 只消费可展示的数据，Runtime 负责真实状态和业务动作。换模型、换存储或换数据层时，不需要重写聊天页面。

02

用 Adapter 连接边界

Runtime 的响应式对象和 UI 的普通数据结构不是同一个契约。Adapter 负责投影、草稿协调、错误捕获和临时 pending。

03

Data 与 Options 分工

Data 表示当前事实；Options 表示静态配置。状态变化进入 Data，产品定制进入 Options。

Design rule

业务变化不应该推动 UI 组件变形

ChatUI 不直接知道 Provider、Conversation 或 MCP Client。它只知道当前应该展示什么，以及用户触发了什么事件。

收益： 边界稳定，组件可测试，案例可以通过配置和 Slot 完成定制。

代价：需要维护 Runtime、Adapter、UI 三套明确契约；跨边界的状态变化必须经过事件或数据映射。

事件驱动，而不是把业务回调塞进 Options

提交、会话 CRUD、模型切换、MCP 操作和 Bubble 交互都通过根级 Emits 输出。UI 不等待事件处理，也不伪造成功状态；动作由 Adapter 调用 Runtime 后回到数据流。

每轮请求使用配置快照

发送时将当前模型、能力开关和 MCP 工具选择写入用户消息 metadata。请求开始后再切换设置，只影响下一轮，避免流式过程中读取到变化中的配置。
