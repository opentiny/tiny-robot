# 评论归类与回贴细则

处理一轮 Issue 评论或 PR Review 时，先枚举本轮全部评论，逐条归类并标记处理方式，再动正文。一轮 Review 往往包含异质的多条评论（行级评论、总评、`Request changes` 正文），不要合并成一团笼统处理。

## 权限与 bot 前提

- 评论是否来自授权用户、是否为 bot，以 `article-hub` 的权限与 bot 过滤结果为准，不由自然语言自行判定。
- **已知缺口**：当前 `article-hub` 的固定命令解析与权限/bot 过滤覆盖 Issue 评论；对 PR 的 Review 线程、行级评论、`Request changes` 正文尚无对应 CLI 支撑。处理 PR Review 评论前，必须由人工确认评论者具备仓库写权限，不要仅凭评论内容推断授权。这是临时约束，不是让 Agent 自行实现权限判定。

## 触发规则（来自需求 §15.4）

- `Request changes`：收集该 Review 中的全部意见并触发修订。
- 普通行级评论或普通 PR 评论：只有以 `/ai` 开头才触发；`/ai 全文润色` 按一轮全文修订处理。
- `Approve`、人工说“通过/确认”：只更新审核状态，不触发修改。

## 归类（先判类型，再决定怎么处理）

逐条归入下列之一：

1. **固定控制命令**（`/ai 状态`、`/ai 批准写作计划`、`/ai 暂停`、`/ai 恢复`、`/ai 重试` 等）：不属于正文润色范围，交由 generate 流程或 CLI 处理，polish 不消费。
2. **正文局部修订**：指向具体段落、表达、结构的明确修改要求，且不触及受保护内容。默认只改评论指向处。
3. **需回源核验的事实类**：触及版本、API、兼容性、性能、安全、代码等受保护事实。无论评论者是运营还是技术，都回固定来源核验；无法核验则停下并请技术维护者确认，不靠改措辞掩盖不确定性。
4. **模糊待澄清**：意图不清、只表达感受、存在多个互斥改法或意见互相冲突。按 SKILL 停止条件先澄清，不猜测改法。
5. **越权 / 超范围 / 无法采纳**：越过本轮授权章节、要求新增来源外事实、或与固定来源冲突。不执行，逐条说明原因。

判定处理边界**按是否触及受保护内容**，不按评论者身份区分。运营也可能提出触及事实的意见，技术也可能只提表达意见。

## 逐条处理与回贴

- 按归类逐条处理，处理范围不外溢到未被评论覆盖的章节。
- 完成后逐条回贴本轮处理结果，每条标注：已改（附对应 Commit 或改动位置）/ 需澄清（附待确认问题）/ 超范围或拒绝（附原因）。
- 只回复修改内容、对应 Commit 和待确认项，**不自动 Resolve conversation**；由原评论作者确认后手动 Resolve 即可。
