# 文章类型与结构参考

写作前按 `article_type` 读对应小节，确定结构骨架、必备信息、长度区间和默认文风；动笔前先读 [通用写作手艺](./styles/writing-craft.md)，再按 `style_profile` 读 [文风参考](./styles/official-balanced.md) 等对应文件，并深读仓库根目录下的 `materials/style-exemplars/<style>.md` 范例看业界范例如何施展这些手艺（范例文件存在即必读，确实缺失才降级并在对话标注：说明缺哪个范例文件、改按 Skill 内文风文件继续）。

总规则，写作前统一遵守：

- **大纲是推荐而非强制**：类型只规定必须覆盖的信息，不强制固定的章节标题和顺序。资料不足时降低覆盖范围或在写作计划里标为缺口，不要为了凑齐推荐章节而编造内容（这类问题对应润色 Skill 反模式里的“机械结构”）。
- **长度不是硬性验收指标**：区间用于判断是否写得过单薄或过冗长。预计超过约 6000 字时，写作计划应建议拆分，拆分后每篇用独立 Issue。
- **默认以「关于 OpenTiny NEXT」收尾**：所有类型默认在正文最末尾追加该收尾章节，文案套用 [收尾章节模板](./about-opentiny-section.md)；下文各类型「推荐大纲」不再重复列出该章节。仅当选题/写作计划阶段人工以自然语言明确表示不要时省略。
- **动笔前先定主线**：用一句话声明本文主线（一条真实调用链 / 一个具体问题 / 一个决策处境），章节服从主线推进、模块在主线需要时才登场，首段用具体问题或场景开篇；不是模块并列 / 逐模块·逐文件·逐能力平推（最常见的走偏）。动笔前的具体配方与自审闸门见生成 Skill 第 6 步，本处只列原则。

每个类型给出：必备信息、推荐大纲、长度区间、默认文风、好文特征、常见走偏。必备信息与长度区间来自 `docs/article-generation-requirements.md` §4.2、§12.5，是事实依据，不要私自改写。

## release（版本发布解读）

- **必备信息**：目标版本、核心变化、用户价值、兼容性、升级注意事项、已知限制。
- **推荐大纲**：本次版本概览 → 核心变化逐项说明（每项给出“变了什么 + 对用户意味着什么”）→ 兼容性与升级注意 → 已知限制与后续计划。
- **长度**：约 1500–3000 字。
- **默认文风**：[release-promotional](./styles/release-promotional.md)。
- **好文特征**：每条变化都落到具体能力、配置或 API，而不是停留在“更强大、更智能”；升级注意和已知限制与新特性同等可见，不只报喜。
- **常见走偏**：写成纯营销稿，只堆形容词不给版本号、变更项和限制条件；把实验特性写成正式能力。

## practical-guide（特性、教程、性能优化、问题排查）

- **必备信息**：使用场景、前置条件、步骤或方法、注意事项、验收方式。
- **推荐大纲**：要解决的问题与适用场景 → 前置条件（版本、依赖、环境）→ 步骤或方法（关键步骤配可运行代码）→ 注意事项与常见坑 → 如何验证生效。
- **长度**：约 2500–5000 字。
- **默认文风**：[developer-friendly](./styles/developer-friendly.md)。
- **好文特征**：步骤可被读者照着复现，每段代码都说明前置条件和预期结果；明确标出哪些是必需步骤、哪些是可选优化。
- **常见走偏**：跳过前置条件直接贴代码；把“能用”写成“最佳实践”却无来源；只给配置不给验证方式。

## source-analysis（源码与架构解析）

- **必备信息**：模块关系、关键链路、实现机制、边界与限制。
- **推荐大纲**：从一条真实调用链或一个具体问题切入 → 涉及的模块与职责关系 → 关键链路逐步拆解（引用固定 SHA 的源码）→ 实现机制中的关键设计 → 边界、限制与未覆盖部分。
- **长度**：约 3000–6000 字。
- **默认文风**：[technical-deep-dive](./styles/technical-deep-dive.md)。
- **好文特征**：围绕一条主线链路展开，给出模块间的关系而非逐文件罗列；明确实现的边界与本文未覆盖的部分；所有代码引用绑定确定的分支或 Commit。
- **常见走偏**：写成 API 字典或逐模块/逐文件平推（「第一类/第二类…」骨架、每节复述文档）；把当前实现描述成“唯一正确设计”；引用未固定版本的源码导致结论站不住。
- **主线骨架示范**（以「AI 组件库 vs 传统组件库的职责边界」为例，对照模块清单与主线骨架；同题材可迁移）：

```text
❌ 模块清单（按包分节，调换/抽章不影响 → 平推）：
   定位 → Bubble 能做什么 → Sender 能做什么 → Kit 能做什么 → CLI 能做什么 → 场景
✅ 主线骨架（同一条对话贯穿，模块按需登场）：
   主线 = 跟随一次「用户提问 → 流式回复 → 工具调用 → 切换历史会话」，看每一步前端职责落在传统组件库还是 AI 组件库
   ① 用户敲下问题：输入意图为何超出普通输入框（输入增强组件在此登场）
   ② 请求发出到流式返回：消息状态与 SSE 谁来管（数据层在此登场）
   ③ 富内容要渲染：消息气泡为何不是普通列表项（展示组件在此登场）
   ④ 切换历史会话继续：多会话状态边界（会话管理在此登场）
   同一条对话贯穿四步、调换即断裂；不是给每个包各开一节罗列能力。
```

## case-study（项目案例与实践复盘）

- **必备信息**：项目背景、实施过程、问题、结果、经验与适用边界。
- **推荐大纲**：项目背景与目标 → 实施过程的关键决策 → 遇到的问题与应对 → 结果（尽量给可核验的事实）→ 经验与适用边界（哪些可复用、哪些是特定前提）。
- **长度**：由资料完整度决定，建议不超过约 6000 字。
- **默认文风**：[official-balanced](./styles/official-balanced.md)。
- **好文特征**：结果用可核验的事实而非主观成效描述；经验明确划出适用边界，不夸大为普适方法论。
- **常见走偏**：把个案经验写成行业规律；用没有来源的“效率提升 X%”充当结果；隐去失败与限制只讲成功。
