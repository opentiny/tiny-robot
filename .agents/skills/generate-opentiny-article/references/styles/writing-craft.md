# 通用写作手艺（写作前先读）

本文件教"该往文章里加什么有信息量的东西"，与润色 Skill 的 `anti-patterns.md`（教"删什么没信息量的壳"）互补：一个管上限（值得读），一个管下限（别写坏）。两者不冲突——这里要求的钩子、判断、细节都必须落到固定来源已有的事实；凡是落不到事实的"好看"都不写。

适用于全部四种文风。具体到某文风怎么用，见同目录对应文风文件；动笔前必读仓库根目录下的 `materials/style-exemplars/<style>.md`，看真实范例如何施展这些手艺——只读手艺描述容易写成「文档腔」，范例才示范手艺如何落到真实文章。范例文件存在即读，确实缺失才降级并在对话标注：说明缺哪个范例文件、改按 Skill 内文风文件继续。

下面四项，对应"读起来像业界高质量文章、而非生成式文档"最常缺的东西。每项给：原则、为什么、一个一两句的形态对照、与克制底线的边界。形态对照里的例子只示范写法，不是要照搬其主题或措辞。

## 1. 钩子：用具体问题/反常识/真实场景开篇，而不是定义

- 为什么：定义式开场（"X 是一种……"）不给读者读下去的理由；好文章第一段就制造"我得知道答案"的张力。
- 形态对照：
  - 平：「Sender 是 TinyRobot 的输入区组件，支持单行多行、快捷键和扩展。」
  - 好：「同样是个输入框，为什么 Sender 要把提交、换行、字数统计拆到不同的 composable 里？先看一次提交里实际发生了什么。」
- 边界：钩子必须落到本文真实事实与真实问题，不为制造悬念编造场景、用户或数据。

## 2. 判断：罗列之前，先给一句作者的判断/取舍/坑

- 为什么：纯复述代码或功能就是文档；先给判断，读者才知道"有人在替我看门道"。
- 形态对照：
  - 平：「Sender 提供 Template、Mention、Suggestion 三种扩展。」
  - 好：「Template、Mention、Suggestion 常被当成同一种'下拉列表'混用——一旦混用，提交出来的数据语义就乱了。它们其实解决三个不同问题：」
- 边界：判断必须有来源支撑，落到原文已有的行为、条件、结果或限制；不把普通实现拔高成"唯一正确设计"或行业变革。

## 3. 主线：全文围绕一条主线推进，详略有致，不逐模块平推

- 为什么：按文件/模块顺序逐个介绍会变成流水账；一条主线（一次真实调用、一个具体问题、一次决策）能把零散模块串成有去向的叙述。
- 形态对照：与其"第一节讲主组件、第二节讲 composable、第三节讲扩展"逐块平铺，不如选"一次提交的数据如何从编辑器流到业务侧"做主线，让每个模块在主线需要时才登场。
- 边界：不为叙事牺牲准确；操作步骤、参数清单、API 表等天然需要结构化的内容保留其结构，不强行叙事化。

## 4. 具体：用对比、数字、最小例子让抽象落地

- 为什么：抽象概括（"更准确""更灵活"）记不住也无法核验；具体的对象、数字、最小例子才有画面感和可信度。
- 形态对照：
  - 平：「v0.4 让字数统计更准确了。」
  - 好：「字数统计从'按字符串长度数'改成'按 grapheme 数'（对应 PR #313），于是一个 emoji 不再被算成好几个字符。」
- 边界：数字、例子、对比都必须真实可核验、来自固定来源；缺数据时降低结论强度，不补造示例充门面。

## 与 brand/writing-style.md 的关系

仓库里的 `references/brand/writing-style.md` 记录的是 OpenTiny 自家发布套路、标题习惯和社区传播用语，偏营销。遇到它偏夸张的措辞习惯（"重磅""一招搞定"式），以本 Skill 的克制底线与润色 Skill 的 `anti-patterns.md` 为准：可以借它了解 OpenTiny 的固定表达和生态位，但"有阅读欲望"靠的是上面四项手艺，不是靠形容词。
